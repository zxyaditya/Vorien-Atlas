# Atlas Backtest Engine: Architecture and Implementation

## 1. Executive Summary

The Atlas Backtest Engine is an institutional-grade, event-driven simulation framework designed to evaluate quantitative hypotheses generated by the Atlas Learning System. It guarantees deterministic simulation execution, exact state replication, and comprehensive risk analytics.

Integrated directly with the `learning_system` module, the Backtest Engine processes predictive signals (from XGBoost, LightGBM, or TFT sequence models) and translates them into execution directives, tracking equity, drawdowns, and portfolio state through a high-performance Pythonic state machine.

---

## 2. Configuration: The BacktestSpec

Every backtest is instantiated via a `BacktestSpec` dataclass, ensuring that the rules of engagement are immutably logged before execution begins.

### 2.1 Core Parameters
- **Initial Capital:** Starting cash (default: 100,000 USD).
- **Fees:** Expressed in basis points (bps) for maker and taker execution.
- **Slippage:** Slippage model (fixed bps, or volume-dependent impact).
- **Time Ranges:** Start and end timestamps for the simulation boundary.
- **Data Resolution:** Tick, 1m, 5m, 1h, or daily OHLCV.

### 2.2 The StrategyPolicy
The `StrategyPolicy` governs how raw model probabilities are converted into sizing and risk management decisions:
- **Upper/Lower Thresholds:** Activation thresholds for the model's `probability_up` prediction.
- **Allow Short:** Boolean flag to enable/disable short selling.
- **Position Size Pct:** Fixed percentage of equity to risk per trade.
- **Max Leverage:** Absolute cap on portfolio gross exposure.
- **Stop Loss / Take Profit:** Fixed percentage limits.
- **ATR Stops:** Trailing stops governed by the Average True Range to adapt to volatility.
- **Trailing Stops:** High-water mark activation.
- **Kelly Criterion & Dynamic Sizing:** Advanced position sizing that scales `position_size_pct` proportionally to the model's predicted edge (probability - 0.5) and historical win rate.

## 3. The Execution Engine Abstraction

Atlas utilizes a strictly typed abstract contract for order routing to ensure that moving from backtest to paper trading to live trading requires zero logic changes in the core engine.

### 3.1 `ExecutionEngine` Contract
```python
class ExecutionEngine(ABC):
    @abstractmethod
    def submit_order(self, order: Order) -> OrderResult: pass
    
    @abstractmethod
    def cancel_order(self, order_id: str) -> bool: pass
    
    @abstractmethod
    def get_portfolio_state(self) -> PortfolioState: pass
```

### 3.2 `PaperExecutionEngine`
The simulation workhorse. Logic entails:
- **Opening Trades:** Validates margin, calculates base adverse slippage, deducts taker fees, and appends to the open trades ledger.
- **Closing Trades:** Executes opposite-side sizing. Applies maker/taker fees appropriately (stop-market vs limit take-profit).
- **Slippage Application:** $\text{Price}_{\text{fill}} = \text{Price}_{\text{mid}} \cdot (1 \pm \text{slippage\_bps} / 10000)$

## 4. Portfolio State Machine

The core ledger of the backtest is maintained by the `Portfolio` class.
- **Cash:** Unencumbered capital available for margin.
- **Open Trades:** Dictionary of currently active `Trade` objects.
- **Closed Trades:** Append-only list of completed round-trip trades.
- **Equity Tracking:** Mark-to-market calculations performed at every tick/candle.

### 4.1 The `Trade` Dataclass
Every transaction maps to a definitive `Trade` object capturing the exact lifecycle of the risk event:
- `trade_id`: UUID
- `direction`: LONG / SHORT
- `open_time` / `open_price`: Entry parameters
- `close_time` / `close_price`: Exit parameters
- `size`: Absolute base currency size
- `fee_paid`: Total accumulated commission
- `pnl`: Absolute profit/loss
- `return_pct`: Unlevered return percentage
- `open_reason`: e.g., "SIGNAL_THRESHOLD_EXCEEDED"
- `close_reason`: e.g., "STOP_LOSS", "TAKE_PROFIT", "SIGNAL_REVERSAL", "END_OF_BACKTEST"

## 5. Walk-Forward Backtesting

To prevent overfitting, the Backtest Engine supports native **Walk-Forward Backtesting**.
Instead of evaluating a model on a single out-of-sample holdout, the engine rolls forward through time:
1. Train on $T_1 \dots T_k$.
2. Backtest on $T_{k+1} \dots T_{k+n}$.
3. Train on $T_2 \dots T_{k+1}$ (or expanding window $T_1 \dots T_{k+1}$).
4. Backtest on $T_{k+n+1} \dots T_{k+2n}$.

The portfolio state is seamlessly handed off between periods to generate a continuous, stitched equity curve that accurately reflects the compounding effects of a continuously retrained ML pipeline.

## 6. Equity Curve and Metrics

### 6.1 Mark-to-Market Logic
At each time step $t$, the system constructs an `EquityPoint`:
- Timestamp
- Cash
- Unrealized PnL (Open Positions)
- Total Equity
- Drawdown from Peak

### 6.2 `BacktestMetrics` Computation
The engine computes institutional-grade statistics over the `closed_trades` and the equity curve:
- **total_return_pct:** Terminal Equity / Initial Capital - 1
- **sharpe:** Annualized return divided by annualized volatility of returns.
- **max_drawdown_pct:** Maximum peak-to-trough drop in the equity curve.
- **n_trades:** Statistical significance metric.
- **win_rate:** % of trades with $\text{PnL} > 0$.
- **profit_factor:** Gross Profit / Gross Loss.
- **calmar:** Annualized Return / Max Drawdown.
- **sortino:** Downside-deviation adjusted Sharpe.

## 7. Persistence and BacktestTracker

All backtest runs are rigorously tracked to maintain research provenance.

### 7.1 MongoDB Integration
The `BacktestTracker` interfaces with MongoDB's `learning_backtests` collection.
It stores:
- Backtest ID & Experiment ID
- Execution latency & timestamps
- Complete `BacktestMetrics` payload
- Complete `StrategyPolicy` payload

### 7.2 Intentional Payload Optimization
The `trades` array and `equity_curve` are intentionally **excluded** from the high-frequency list endpoints:
- **Rationale:** A backtest over 5 years of 1m data can generate millions of `EquityPoint` objects and thousands of `Trade` records. Serializing this to MongoDB for dashboard list views can saturate network bandwidth and memory.
- **Solution:** Heavy artifacts (trades, full equity curves) are written to MinIO as compressed parquet files, while only high-level `BacktestMetrics` remain in MongoDB for fast querying, filtering, and sorting.

---

## 8. Performance Characteristics & Optimizations

1. **Sequential State Iteration:** Chronological sequential iteration over the OHLCV matrix is preserved because trades are path-dependent (a stop-loss relies on prior state, making naive vectorization inapplicable for dynamic sizing).
2. **Numba/JIT Acceleration:** Execution logic in `PaperExecutionEngine` leverages optimized NumPy arrays and Numba JIT compilation where appropriate to minimize per-bar latency.
3. **Memory Footprint:** The backtester strictly uses view-based slices to avoid copying DataFrames during walk-forward boundary generation.

The Atlas Backtest Engine bridges the gap between theoretical predictive power (Learning System) and real-world execution. By modeling nuanced slippage, exact fee structures, path-dependent state machines, and dynamically scaling Kelly criterion constraints, it ensures that the Sharpe ratios reported by the ML layers survive contact with market microstructures.
